# Single-turn assistant runtime

The `vela-kernel` crate provides a synchronous, provider-neutral boundary that executes one tool-free assistant turn over an existing persisted session.

## Observable contract

- `AssistantProvider` receives the complete ordered persisted transcript after the current human turn has committed. It returns one validated `SessionTurnContent`; provider adapters own request conversion and response validation beyond the kernel's existing non-empty content rule.
- `AssistantRuntime<P>` owns session and task stores over the same typed SQLite event log plus a caller-supplied provider. `AssistantRuntime::open` opens those stores and performs no provider work.
- `AssistantRuntime::execute_turn` first appends the supplied content as a human turn, calls the provider exactly once with the resulting transcript, then appends the returned content as an assistant turn. Success returns the updated `Session`; both turns survive reopening the store.
- Missing and closed sessions return `RuntimeError::Session` before provider invocation and append no turn.
- Provider failure returns `RuntimeError::Provider`. The human turn remains durable and no assistant turn is synthesized. `ProviderError` retains the adapter-specific standard error as its source, and `RuntimeError` retains `ProviderError` in its source chain.
- The runtime never retries provider calls because an invocation may have external effects. A caller-requested retry is a new turn invocation and therefore persists another human turn.
- If the assistant append fails after provider success, the session error is returned. The previously committed human turn remains durable; there is no rollback across the external provider call.
- `AssistantProvider` and `AssistantRuntime` are synchronous. The caller owns provider construction, model selection, credentials, timeout behavior, and any serialization needed to ensure only one invocation is in flight for a session.
- Existing session event payloads and replay projections are unchanged. The provider sees existing `SessionTurn` values, so the durable transcript remains the source of truth.

## Explicit composed skill turns

`SkillRegistry::select` borrows only caller-supplied exact IDs for one request. It rejects the lexicographically first duplicate before checking presence, then rejects the lexicographically first absent ID; either failure leaves the process-local registry unchanged. A successful selection exposes immutable `RegisteredSkill` references in ascending exact-ID order and preserves every instruction byte. Registration alone remains inert, and an empty selection is valid.

`AssistantRuntime::execute_composed_turn` is the additive tool-free composition boundary. The caller supplies typed `SystemPolicy` and `DeveloperPolicy` values, a registry, and exact IDs for that request. `ComposedAssistantRequest` exposes four structurally distinct fields in descending authority order: system policy, developer policy, selected skill blocks, and the complete durable transcript. The kernel does not concatenate those fields; a `ComposedAssistantProvider` adapter may lower them into provider-native roles without promoting skill instructions above caller policy.

Selection completes before any transcript write or provider invocation. After selection, composed execution has the ordinary durable ordering: append the human turn, call the composed provider exactly once, then append its assistant response. Provider failure leaves the human turn committed, appends no assistant turn, and retains the adapter error in the existing `RuntimeError::Provider` source chain. `execute_turn` and every existing task or tool-capable method continue to use their original provider boundaries and never receive registered skills implicitly.

## Explicit composed bounded tool steps

`execute_composed_provider_tool_step` is the additive low-level composition boundary for one provider call and at most one tool invocation. It validates caller-selected exact skill IDs before the provider, authorization, adapter, or invocation store can be reached. `ComposedToolAssistantRequest` exposes system policy, developer policy, selected skills, transcript, and deterministic tool metadata as separate typed fields. The first four retain their documented instruction authority; tool metadata is descriptive capability data and grants no permission.

A final provider response returns without authorization or tool evidence. A successful tool request uses the existing task-associated durable registry dispatch and returns exact input/output only in memory. `ComposedProviderToolStepOutcome::continuation` borrows an opaque continuation containing the exact initial policies, selected skill blocks, transcript, and prior result. `continue_composed_provider_tool_step` refreshes current tool metadata but provides no API to replace that retained composition. Each subsequent request requires a fresh caller-owned invocation ID and authorizer and advances only through another explicit operation; skills never authorize tools and Vela never runs an automatic loop.

Selection failures are exposed separately from the existing provider/tool step error. Provider, lookup, task-validation, authorization, adapter, and persistence failures retain the existing source chain and durable invocation prefixes through the composed wrapper. Existing `ToolAssistantProvider`, `ToolAssistantContinuationProvider`, and low-level skill-free operations are unchanged; durable task composition is an additive boundary described below.

## Durable composed attempt turns

`ToolAssistantRuntime::execute_composed_task_turn` integrates the same typed composition into one durable attempt-producing task turn. The caller supplies system policy, developer policy, a process-local skill registry, and exact selected IDs in addition to the existing task, observation, invocation, registry, and authorization inputs. Duplicate or missing skill selection fails before task/session writes, provider work, authorization, adapter execution, or invocation evidence. A successful selection is followed by the existing active-task, immutable-association, writable-session, unique-observation, and fresh-invocation preflight.

For tool-free workflow-phase evidence, `AssistantRuntime::execute_workflow_phase_task_turn` resolves one exact borrowed phase after active-task, fresh-Attempt, and writable-session preflight, then commits the successful assistant response and matching Attempt atomically. `execute_workflow_phase_task_correction_turn` and `execute_workflow_phase_task_diagnostic_turn` apply the same composed phase authority to a fresh Correction or Diagnostic linked to one caller-selected existing Attempt. Each validates its exact lineage before transcript or provider effects and commits the final assistant turn with the matching evidence atomically, without creating a new Attempt. A model-produced Diagnostic remains analysis evidence rather than independent Verification or a task-failure reason. `complete_workflow_phase_task_turn` is the caller-requested completion counterpart: it validates the response as both Attempt text and task output, atomically commits the assistant turn and Attempt, then completes the task with that exact output. `fail_workflow_phase_task_turn` and `cancel_workflow_phase_task_turn` instead retain an already validated caller-owned diagnostic or reason, atomically commit the response only as assistant content and Attempt evidence, then apply that exact terminal intent. None of these operations infer a workflow run or persist phase provenance.

Phase-assisted completion, failure, and cancellation preserve the established ordered terminal prefix. Provider failure or a blank-only response leaves only the committed human turn. A response-append race writes neither assistant content nor the requested Attempt, while a task terminal race after the atomic response append preserves that assistant turn and Attempt and reports the authoritative winning terminal state. Completion provider content is exact task output, while failure and cancellation provider content never becomes the caller-owned diagnostic or reason; none is independent `Verification` evidence. These operations do not acknowledge a workflow gate, choose a transition, or mutate, complete, fail, or cancel a workflow.

The initial provider sees the selected composition, human-inclusive durable transcript, and current deterministic tool metadata as distinct fields. Final content commits an assistant turn followed by an exact `Attempt`. A tool request uses the existing task-associated durable invocation protocol, writes no assistant turn or Attempt, and returns `ComposedToolTaskTurnOutcome::ToolCompleted`. Its borrowed continuation retains the originating task, transcript, policies, exact-ID-ordered selected skill blocks, and exact in-memory tool result without setters or replacement inputs.

`continue_composed_task_turn` revalidates the active task, association, open and unchanged transcript, unique Attempt ID, and fresh invocation ID before calling the composed continuation provider once. It refreshes descriptive tool metadata only. A final response conditionally appends against the retained transcript and then records the Attempt; another tool response returns the same immutable composition with the new exact result. Every tool step still requires a fresh caller-owned invocation identity and authorizer. Existing skill-free task operations remain unchanged.

`execute_composed_task_correction_turn` and `continue_composed_correction_task_turn` extend that boundary only to correction-producing turns. Skill selection still completes before task lineage validation or any side effect. The initial operation validates the caller-selected parent Attempt and Correction identity, while each opaque continuation retains that parent together with the exact policies, selected skill blocks, transcript, and prior in-memory tool result. A final response conditionally appends the assistant turn and then records one exact `Correction` linked to the retained parent; another tool response writes neither and requires a fresh explicit continuation. Stale transcripts, invalid lineage, invocation identity, and authorization use the existing fail-closed boundaries, and skill-free correction methods are unchanged.

`complete_composed_task_turn` and `continue_composed_completion_task_turn` add caller-owned completion intent without changing the skill-free completion API. They retain the exact policy and selected-skill context across explicit tool continuations and reuse the active-task, association, writable-session, transcript, observation, invocation, and authorization preflights. A final response commits the assistant turn, exact `Attempt`, and completion in that order; the task output is exactly the final assistant content. A tool result remains non-terminal and in memory.

`fail_composed_task_turn` and `continue_composed_failure_task_turn` extend the same boundary only to caller-owned failure intent. The initial operation accepts an already validated `TaskFailure`; skill selection and diagnostic construction therefore complete before task, session, invocation, provider, or tool side effects. Each opaque continuation retains the exact diagnostic with the immutable policy, selected skills, task, transcript, and latest in-memory tool result. A final response commits the assistant turn and exact `Attempt`, then fails the task with the retained diagnostic. Provider content is attempt evidence only: it is neither terminal detail nor `Diagnostic` or `Verification` evidence. Stale or terminal continuations fail during the existing preflights before provider or tool work.

`cancel_composed_task_turn` and `continue_composed_cancellation_task_turn` provide the symmetric caller-owned cancellation boundary. They accept and retain an already validated `TaskCancellation` with the immutable authority and in-memory tool context. Selection failures precede all side effects; stale and terminal continuations fail before provider or tool work. A final response commits the assistant turn, exact `Attempt`, and retained cancellation reason in order. Provider content remains Attempt evidence only, and the operation records a decision rather than interrupting provider or tool work already in flight.

## Independent task verification

`TaskVerifier` is a synchronous caller-owned checker boundary separate from every assistant provider. `AssistantRuntime::verify_task_attempt` accepts an active task, exact existing parent Attempt, fresh Verification ID, and borrowed verifier. It validates task status and exact lineage before invoking the verifier once, and `TaskVerificationRequest` exposes immutable references to the loaded task and selected Attempt. The operation does not require a session association.

A successful non-blank checker result is appended as `TaskObservationKind::Verification` linked to that Attempt. Verifier failure returns `RuntimeError::Verifier`, blank output returns `RuntimeError::InvalidVerificationText`, and neither writes evidence. A racing task or observation change remains authoritative at append and does not retry the verifier. Verification writes no transcript turn, never invokes the owned assistant provider, does not infer a typed pass/fail status from opaque text, and does not transition task or workflow state.

## Task-associated turns

`AssistantRuntime::execute_task_turn` connects the same single-turn sequence to one existing task. The caller supplies the task ID, human content, and a caller-owned observation ID. The task must be active and already associated with a session; missing, completed, cancelled, failed, and unassociated tasks fail before a transcript write or provider invocation. A closed associated session is rejected by the existing session boundary before provider invocation.

On success, the runtime returns a `TaskTurnOutcome` containing the durable `Session` and `Task` projections. After both transcript turns commit, it appends one `TaskObservationKind::Attempt` whose ID is the supplied ID and whose text is exactly the assistant content. Reopening either store reproduces the returned projections.

`AssistantRuntime::execute_task_correction_turn` is the explicit correction-producing counterpart. The caller additionally supplies the ID of an earlier attempt in the same task. Before writing a transcript turn or invoking the provider, the runtime applies the same active/association checks and asks the task aggregate to reject a duplicate correction ID, missing parent, or non-attempt parent. It deliberately does not generalize the API to a caller-selected evidence kind: provider turns produce attempts through `execute_task_turn` or corrections through this operation; diagnostics remain store-level or explicit workflow-phase evidence, while Verification enters the runtime only through the separate caller-owned verifier boundary.

After preflight, correction execution uses the same durable human turn, one provider call, and durable assistant turn sequence. It then appends a `TaskObservationKind::Correction` with the caller-owned ID, exact assistant content, and supplied parent-attempt ID. Preflight is not a lock: if the task changes after preflight, the authoritative append reports the winning terminal state or observation error after both transcript turns have committed.

`AssistantRuntime::complete_task_turn` is the explicit caller-requested completion boundary. The caller supplies the final human content and an attempt observation ID; the runtime owns the ordering, but it does not decide autonomously that the task is complete. It preflights the active associated task, uniqueness of the attempt ID, and session writability before invoking the provider. It then commits the human and assistant turns, validates the assistant text as both attempt evidence and task output, appends an `Attempt`, and completes the task with exactly the same text. The returned `TaskTurnOutcome` contains the durable transcript and completed task projections. This model response is task output, not `Verification`; verification remains independently observed store-level evidence.

Completion preserves its ordered partial commits. Provider or assistant-append failure writes no attempt or completion. Invalid attempt/output text or an authoritative attempt-append failure preserves both transcript turns but writes no completion. If completion loses a race after the attempt commits, the attempt remains durable and `RuntimeError::Task` exposes the authoritative terminal state. Preflight is not a lock, no provider call is retried, and no cross-stream rollback is attempted.

`AssistantRuntime::fail_task_turn` is the symmetric caller-requested failure boundary. The caller supplies validated `TaskFailure` data in addition to the final human content and attempt ID, so invalid or whitespace-only diagnostics cannot enter the operation. The runtime preflights the same task, observation, and session constraints, commits both transcript turns, appends the provider response only as an `Attempt`, and then fails the task with the exact caller-owned diagnostic. Model text is never reclassified as `Diagnostic` or `Verification` evidence.

Failure execution preserves the same ordered durable prefixes. Provider or assistant-append failure writes no attempt or terminal failure. Invalid attempt text and authoritative attempt-append errors preserve both transcript turns without failing the task. If the terminal failure loses a race after the attempt commits, that attempt remains durable and the winning terminal state is returned as `RuntimeError::Task`. No provider call is retried and no cross-stream rollback is attempted.

`AssistantRuntime::cancel_task_turn` is the caller-requested cancellation counterpart. The caller supplies validated `TaskCancellation` data along with the final human content and attempt ID. The runtime preflights the active associated task, attempt uniqueness, and writable session, then commits both transcript turns, the provider response as an `Attempt`, and the exact caller-owned cancellation reason in that order. Model text is not the cancellation reason and is not reclassified as another evidence kind.

Cancellation preserves the same ordered durable prefixes and race behavior as failure. Provider or assistant-append failure writes no attempt or cancellation; invalid attempt text and authoritative observation errors preserve the transcript without cancelling; and a terminal race after the attempt preserves that attempt plus the winning state. This operation records terminal intent after a final turn—it does not interrupt a provider call or provide cooperative in-flight cancellation.

The task-associated operations deliberately do not create a cross-stream transaction around an external provider call:

- Provider or assistant-append failure follows the single-turn contract: the human turn remains durable and no task observation is appended.
- Observation failure after assistant persistence returns `RuntimeError::Task` and preserves both transcript turns. The runtime neither retries nor rolls back the provider call. A duplicate caller-supplied observation ID is one deterministic example for attempt turns; correction turns reject known duplicates during preflight but can still encounter a racing duplicate at the authoritative append.
- Session content permits whitespace-only text while task observation text does not. If a provider returns whitespace-only content, both transcript turns remain durable and `RuntimeError::InvalidAttemptText` or `RuntimeError::InvalidCorrectionText` reports why no evidence was appended.
- Task-store and invalid-observation-text failures are retained in the `std::error::Error::source` chain. `TaskNotAssociated` is a source-free runtime domain error.

`RuntimeError` is non-exhaustive. Wrapped session, provider, task-store, and observation-text failures are exposed through `std::error::Error::source`.

## Initial tool-capable task turns

`ToolAssistantRuntime<P>` is an additive bridge from the provider/tool protocol to durable task and session state. It opens session, task, and tool-invocation stores over one SQLite database and owns a `ToolAssistantProvider`; existing `AssistantRuntime`, tool-free methods, and low-level provider-tool step functions are unchanged.

`execute_task_turn` requires an active associated task, a unique caller-owned Attempt observation ID, a writable session, a fresh caller-owned tool invocation ID, a registry, and one caller-owned authorizer. It checks the deterministic task/session/identity constraints before side effects, appends the human turn, and calls the provider exactly once with the resulting durable transcript and deterministic registry metadata.

A final provider response commits an assistant turn and then an Attempt containing that exact content. The returned final outcome contains the durable session and task projections. A successful tool request instead dispatches once through the existing task-associated durable registry path and returns the durable human-only session plus exact in-memory input/output with `ProviderRequired`. It writes no assistant turn or Attempt. `ToolTaskTurnOutcome::continuation` returns a borrowed continuation bound to the originating task, and `ToolAssistantRuntime::continue_provider_step` remains available for one explicit low-level continuation that does not persist provider content.

`ToolAssistantRuntime::continue_task_turn` is the additive durable continuation boundary. The caller supplies the prior task-bound continuation, a unique Attempt observation ID, a fresh invocation ID, a registry, and one-invocation authorizer. Before calling the same owned provider exactly once, the runtime requires the originating task to remain active and associated, the associated session to remain open with a transcript exactly equal to the continuation snapshot, the Attempt ID to remain unused, and the invocation ID to remain fresh. A stale transcript is rejected explicitly rather than sending obsolete context to the provider; a final assistant append also uses an atomic transcript guard so a turn racing the provider call preserves only the winning turn and reports staleness.

A final continuation commits the exact assistant content followed by an Attempt with the same text and returns reopened-equivalent session/task projections. A subsequent tool request dispatches exactly once, appends no transcript turn or Attempt, and returns the unchanged durable session plus the next exact in-memory continuation. This is caller-controlled progression, not an automatic loop: every additional provider step requires another explicit operation and identities. Exact tool inputs and outputs stay in memory; durable invocation events remain metadata-only.

`ToolAssistantRuntime::execute_task_correction_turn` and `continue_correction_task_turn` are the correction-producing counterparts. The caller supplies an earlier Attempt ID plus a fresh Correction ID. The runtime preflights that lineage with the same active-task, association, transcript, and invocation constraints before side effects. A tool response remains non-terminal and returns a correction-specific continuation that retains the parent Attempt identity only in memory. A final response appends the assistant turn and a Correction containing the exact provider text linked to that caller-owned Attempt; it appends no new Attempt and leaves the task active.

Correction preserves the same ordered prefixes and authoritative races as attempt-only turns. Invalid Correction text or an authoritative correction append error preserves the transcript without synthesizing other evidence. Provider text is never promoted to Diagnostic or Verification evidence, and correction continuations cannot be passed to attempt-only or terminal operations.

`ToolAssistantRuntime::complete_task_turn` and `continue_completion_task_turn` are the explicit caller-requested completion counterparts. They preserve the same bounded initial and continuation steps while returning a distinct `ToolTaskCompletionOutcome` whose continuation cannot be passed to attempt-only operations. A tool response remains non-terminal and requires another explicit completion continuation; it writes no assistant turn, Attempt, or completion. A final response commits the assistant turn, an Attempt with the exact response, and task completion with the same response as output, in that order. The caller therefore retains completion intent, identity, authorization, and progression across every tool step.

Completion preserves ordered partial commits. Provider and invocation failures retain the same prefixes as attempt-only turns. Invalid Attempt or output text preserves both transcript turns without completion. An Attempt append failure preserves the transcript, while a terminal race after the Attempt preserves that Attempt and reports the authoritative task state. No provider or tool call is retried and no cross-stream rollback is attempted.

`ToolAssistantRuntime::fail_task_turn` and `continue_failure_task_turn` are the explicit caller-requested failure counterparts. The caller supplies a validated `TaskFailure` before the initial step; failure-specific outcomes and continuations retain that exact diagnostic across every bounded tool step. A tool response remains non-terminal and writes no assistant turn, Attempt, or failure. A final response appends the assistant content and an Attempt with the same provider text, then fails the task with the caller-owned diagnostic. Provider text is evidence only and is never promoted to the failure reason.

Failure preserves the same ordered partial commits and authoritative races as completion. Provider and invocation errors retain their established durable prefixes. Invalid Attempt text or an Attempt append error preserves the transcript without failing the task, while a terminal race after the Attempt preserves the Attempt and reports the winning state. No provider or tool call is retried and no cross-stream rollback is attempted.

`ToolAssistantRuntime::cancel_task_turn` and `continue_cancellation_task_turn` are the explicit caller-requested cancellation counterparts. The caller supplies a validated `TaskCancellation` before the initial step; cancellation-specific outcomes and continuations retain that exact reason across every bounded tool step. A tool response remains non-terminal and writes no assistant turn, Attempt, or cancellation. A final response appends the assistant content and an Attempt with the same provider text, then cancels the task with the caller-owned reason. Provider text is evidence only and is never promoted to the cancellation reason.

Cancellation preserves the same ordered partial commits and authoritative races as failure. Provider and invocation errors retain their established durable prefixes. Invalid Attempt text or an Attempt append error preserves the transcript without cancelling the task, while a terminal race after the Attempt preserves the Attempt and reports the winning state. This boundary records a caller decision after a final turn; it does not interrupt a provider or tool invocation already in flight. No provider or tool call is retried and no cross-stream rollback is attempted.

Failures preserve the ordered prefix. Deterministic preflight failures leave no new turn. Provider failure and post-human pre-intent failures such as unknown tools or task-validation races leave the human turn. Invocation failures after intent commits leave the human turn plus the invocation protocol's authoritative metadata-only prefix. Assistant append failure leaves the human turn; invalid Attempt text or an authoritative task append failure leaves both transcript turns. No provider or tool call is retried, no cross-stream rollback occurs, and exact tool values are not persisted.

## Non-goals

This slice does not add asynchronous execution, streaming, cooperative cancellation, concurrent invocation coordination, automatic retries or tool continuations, provider-specific policy serialization, provider/model metadata, credentials, concrete external tools, model-owned permissions, token accounting, automatic skill routing, skill persistence, precedence, dependencies, automatic task creation, association, generic caller-selected evidence kinds, generic runtime diagnostic turns outside the explicit parented workflow-phase Diagnostic boundary, typed verification outcomes, executable checker adapters, durable verifier provenance, cross-aggregate transactions, or storage migration. Skills remain unavailable to existing skill-free durable task turns and other `ToolAssistantRuntime` paths; only the explicit composed attempt, correction, completion, failure, and cancellation methods receive caller-selected skills.

See [`session-lifecycle.md`](session-lifecycle.md) for transcript persistence and [`event-log.md`](event-log.md) for durability guarantees.
