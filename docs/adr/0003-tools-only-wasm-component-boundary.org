* ADR-0003: Run first executable extensions as tools-only WebAssembly components
:PROPERTIES:
:CUSTOM_ID: adr-0003-run-first-executable-extensions-as-tools-only-webassembly-components
:END:
- *Status:* accepted
- *Date:* 2026-07-26
- *Owners:* Project Vela maintainers
- *Related issue:* [[https://github.com/Knosence9/project-vela/issues/619][#619]]
- *First execution issue:* [[https://github.com/Knosence9/project-vela/issues/620][#620]]

** Context
:PROPERTIES:
:CUSTOM_ID: context
:END:
Vela can discover immutable extension-registry snapshots and select validated capabilities without opening or executing their entrypoints. The next boundary introduces untrusted executable code, so its capability, ABI, permission, resource, and lifecycle contracts must be explicit before implementation.

The existing architecture calls for isolation around risky tools, a small understandable in-house kernel, caller-owned per-invocation tool authorization, and separate tool, skill, and workflow registries. Native dynamic libraries would execute inside Vela's process. A subprocess protocol would inherit ambient operating-system access unless every supported platform supplied and maintained a separate sandbox.

** Decision
:PROPERTIES:
:CUSTOM_ID: decision
:END:
The first executable extension kind is =tool=. Skill and workflow activation remain unsupported. A caller must provide an =ExtensionSelection= constrained to =ExtensionKind::Tool=; discovery or selection alone never activates code.

A tool entrypoint is a WebAssembly Component Model component implementing the versioned world =vela:extension/tool@0.1.0=. It exports one synchronous function:

#+begin_src wit
package vela:extension@0.1.0;

world tool {
  export invoke: func(input: string) -> result<string, string>;
}
#+end_src

Input and successful output strings contain exactly one UTF-8 JSON value. The host rejects malformed component output. The guest error string is untrusted diagnostic text: it is returned to the immediate caller through the existing sourced tool-error path and is not persisted. The manifest ID becomes the existing =ToolId=. Because version 1 manifests have no effect field, every version 1 tool component is host-classified as =ToolEffect::Pure=; broader effects require a later manifest-version and permission-contract decision.

Activation receives the original extension root with the selection. It reopens each selected manifest parent by descriptor-anchored traversal beneath that root, confirms that it is the selected record's package, then reopens the entrypoint relative to that directory. It rejects symlinks and non-regular files again, reads a bounded component, compiles it, verifies the exact world, and registers an inert adapter in a caller-owned =ToolRegistry=. Activation is all-or-nothing: any unsupported kind, changed manifest or target, invalid component, ABI mismatch, duplicate tool ID, or resource-policy failure leaves the registry unchanged. Compilation and registration must not invoke guest exports.

The runtime uses Wasmtime with the Component Model enabled and no WASI linker. Version =0.1.0= permits no imports, so guests receive no filesystem, network, environment, clock, random, process, credential, host-tool, or kernel access. Unknown imports fail activation. Each authorized invocation receives a fresh store and instance, preventing guest state from becoming an implicit grant or cross-invocation channel.

The host applies explicit limits before guest execution: a bounded component byte size, linear-memory/table/instance limits, fuel, and an epoch deadline. Exhausted limits and traps fail that invocation without retry. Exact numeric defaults are implementation policy rather than ABI and must be documented and tested when introduced. Host process termination, crash containment, and side-channel resistance are not guaranteed by this in-process sandbox.

The existing kernel authorization order remains authoritative. Reading invocation metadata (=id= and =effect=) has no guest effect. A denied request performs no instantiation or guest call. Only after caller-owned authorization may the adapter instantiate the component and call =invoke=. Durable evidence keeps the existing metadata-only retention boundary.

** Alternatives considered
:PROPERTIES:
:CUSTOM_ID: alternatives-considered
:END:
*** Native dynamic library or in-process Rust plugin
:PROPERTIES:
:CUSTOM_ID: native-dynamic-library-or-in-process-rust-plugin
:END:
This offers a straightforward FFI but gives extension code Vela's full process authority and makes memory-safety or ABI faults host faults. It does not satisfy the first isolation boundary.

*** Subprocess JSON protocol
:PROPERTIES:
:CUSTOM_ID: subprocess-json-protocol
:END:
Process separation improves crash containment, but a plain child process inherits ambient operating-system capabilities. Building equivalent filesystem, network, process, and credential isolation across supported systems is larger and less portable than a no-import component boundary. A subprocess worker may later contain the WebAssembly runtime for stronger host crash containment without changing the guest ABI.

*** WASI component imports in version 0.1.0
:PROPERTIES:
:CUSTOM_ID: wasi-component-imports-in-version-010
:END:
WASI would make useful tools easier to build, but preopening directories or exposing clocks, random, sockets, and environment variables would establish a capability-grant model before Vela has one. Version =0.1.0= therefore has no imports.

*** Activate skills and workflows at the same time
:PROPERTIES:
:CUSTOM_ID: activate-skills-and-workflows-at-the-same-time
:END:
Their lifecycle and composition semantics differ from one authorized tool invocation. Combining them would weaken kind routing and enlarge the first trust boundary.

** Consequences
:PROPERTIES:
:CUSTOM_ID: consequences
:END:
*** Positive
:PROPERTIES:
:CUSTOM_ID: positive
:END:
- Untrusted tool code has no ambient host capabilities by default.
- The ABI is language-neutral, versioned, and smaller than Vela's internal Rust traits.
- Existing exact-ID selection and per-invocation authorization remain the routing and permission boundaries.
- Fresh instances make invocation isolation deterministic and easy to explain.

*** Negative
:PROPERTIES:
:CUSTOM_ID: negative
:END:
- Wasmtime adds a substantial dependency and compile-time/runtime cost.
- JSON strings defer richer typed schemas and incur serialization overhead.
- In-process WebAssembly does not isolate Vela from runtime bugs, host exhaustion outside configured limits, or process crashes.
- Useful external-read or mutating tools cannot be components until an explicit host-capability contract exists.

** Verification
:PROPERTIES:
:CUSTOM_ID: verification
:END:
Execution issues must follow RED→GREEN tests proving that activation accepts the exact world, rejects imports and wrong worlds, revalidates changed entrypoints, commits registration atomically, and never calls the guest during compilation or registration. Invocation tests must prove denial precedes instantiation, malformed JSON and traps fail closed, fresh instances do not share guest state, and each configured resource limit terminates the invocation. The repository quality gate must pass.

** Revisit when
:PROPERTIES:
:CUSTOM_ID: revisit-when
:END:
Reconsider the boundary before adding non-tool activation, effects broader than =pure=, host imports, reusable instances, asynchronous calls, streaming or binary payloads, component-to-component calls, persisted activation state, hot reload, subprocess containment, or a remotely distributed extension runtime.
