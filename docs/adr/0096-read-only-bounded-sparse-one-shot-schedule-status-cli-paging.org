* ADR-0096: Read-only bounded sparse one-shot schedule status CLI paging
:PROPERTIES:
:CUSTOM_ID: adr-0096-read-only-bounded-sparse-one-shot-schedule-status-cli-paging
:END:
- *Status:* accepted
- *Date:* 2026-08-08
- *Decision and execution issue:* [[https://github.com/Knosence9/project-vela/issues/995][#995]]
- *Related:* ADR-0090, ADR-0094, ADR-0095

** Context
:PROPERTIES:
:CUSTOM_ID: context
:END:
ADR-0095 exposes bounded sparse one-shot schedule status paging through =ScheduleStore::list_by_status_page=. Operators otherwise need custom kernel code to use it. Client-side composition of ordinary inventory pages with filtering can also misinterpret an empty sparse page as completion or resume from the last emitted match instead of the last inspected schedule.

The CLI adapter must preserve the kernel's explicit storage-work bound and scan-progress cursor without adding dense-fill behavior, a second projection contract, or mutation authority.

** Decision
:PROPERTIES:
:CUSTOM_ID: decision
:END:
Add =vela-dev schedule status-page DATABASE STATUS SCAN_SIZE [AFTER]=. =STATUS= must be exactly =pending=, =cancelled=, =claimed=, or =materialized=. =SCAN_SIZE= must form a positive, at-most-1024 =SchedulePageSize=. Optional =AFTER= must form one exact non-blank =ScheduleId=; it is an exclusive caller-owned scan cursor and need not identify an existing schedule. All inputs are validated before storage access.

The command opens only the selected existing database through =ScheduleStore::open_read_only= and delegates bounded selection, complete selected-window replay, filtering, and continuation to =ScheduleStore::list_by_status_page=. Success emits compact ={"schedules":[...],"next_after":...}= JSON using the existing complete schedule representation. Matching schedules retain exact-ID order and exact caller-authored content is JSON escaped.

=next_after= preserves the kernel's last-inspected semantics. A page may therefore contain no matches and still return a non-null cursor when validated lookahead proves more inventory exists. Terminal, empty, and beyond-end windows return =null=.

Invalid status, scan size, and cursor inputs emit =invalid_schedule_status=, =invalid_schedule_page_size=, and =invalid_schedule_id=. Missing or incompatible storage, selected-window corruption, projection failures, and serialization failures emit =schedule_status_page_inspection_failed=, return non-zero, and emit no partial stdout. Missing storage is never created.

The command reads no ambient clock, mutates nothing, persists no cursor, and grants no dense-fill scan, lifecycle, worker, lease, dispatch, retry, permission, or execution authority.

** Alternatives considered
:PROPERTIES:
:CUSTOM_ID: alternatives-considered
:END:
*** Add paging flags to =schedule status=
:PROPERTIES:
:CUSTOM_ID: add-paging-flags-to-schedule-status
:END:
Rejected because the existing command has a complete fail-closed inventory contract and a different output shape without continuation evidence. An explicit command keeps that behavior compatible.

*** Filter =schedule page= output in callers
:PROPERTIES:
:CUSTOM_ID: filter-schedule-page-output-in-callers
:END:
Rejected because ordinary paging's cursor identifies the last emitted schedule. Sparse status paging must identify the last inspected schedule so an all-nonmatching page can advance safely.

*** Fill a dense page of matches
:PROPERTIES:
:CUSTOM_ID: fill-a-dense-page-of-matches
:END:
Rejected because sparse inventories could require unbounded storage selection, replay, and allocation.

** Consequences
:PROPERTIES:
:CUSTOM_ID: consequences
:END:
- Operators can traverse one-shot schedules by status with explicitly bounded storage work.
- Empty nonterminal pages remain distinguishable from terminal pages.
- CLI continuation and corruption boundaries remain identical to the kernel contract.
- Complete inventory, complete status filtering, and ordinary inventory paging remain unchanged.
- No schema, event, write, clock, or execution authority is added.

** Verification
:PROPERTIES:
:CUSTOM_ID: verification
:END:
Strict RED→GREEN CLI tests prove sparse mixed-status selection, all-nonmatching progress, exact ordering, non-overlapping continuation, nonexistent and beyond-end cursors, terminal and empty output, validation before storage access, missing-storage non-creation, selected and lookahead corruption failure, and isolation outside the selected window. The complete repository quality gate must remain green.

** Revisit when
:PROPERTIES:
:CUSTOM_ID: revisit-when
:END:
Reconsider before adding due-filtered pages, dense matching pages, durable indexes or cursors, snapshot tokens across calls, destructive deletion, clocks, workers, leases, dispatch, permissions, retries, or execution.
