* ADR-0009: Start durable workflow runs from immutable topology snapshots
:PROPERTIES:
:CUSTOM_ID: adr-0009-start-durable-workflow-runs-from-immutable-topology-snapshots
:END:
- *Status:* accepted
- *Date:* 2026-07-28
- *Decision owners:* Project Vela maintainers
- *Related:* ADR-0002, ADR-0006, ADR-0007, ADR-0008, issues #687 and #688

** Context
:PROPERTIES:
:CUSTOM_ID: context
:END:
ADR-0008 advances one registered workflow through a deterministic caller-owned cursor, but the cursor and the registry topology it borrows disappear with process memory. Durable advancement cannot safely refer only to a workflow ID: a later registry could omit or replace that ID, making replay depend on mutable ambient state. Vela already has a typed append-only SQLite event log whose streams provide optimistic creation and fail-closed versioned replay.

The first durable boundary should preserve the definition that a run actually selected without also deciding transition events, action execution, scheduling, or recovery policy.

** Decision
:PROPERTIES:
:CUSTOM_ID: decision
:END:
The kernel stores each workflow run in its own =workflow-run:<exact run ID>= event stream. A =WorkflowRunId= is an opaque caller-supplied non-blank UTF-8 value. Starting an existing exact run ID fails atomically.

A version-one =workflow_run.started= event owns the exact registered workflow ID and complete authored topology: start ID, ordered phases, terminal markers, ordered transition targets, and optional exact gate IDs. This immutable snapshot is the run's definition provenance. Loading a run reconstructs its owned definition from the event and never consults a workflow registry, package, manifest, or filesystem.

Start first applies the existing cursor's exact start-resolution check. Missing or ambiguous starts fail before append. A successful start remains at that exact declared phase and performs no transition. Replay accepts exactly one supported start event, validates its strict payload and workflow identity, resolves the exact start again, and rejects unsupported events, malformed payloads, or any other history shape without returning partial state.

The returned =WorkflowRun= is read-only in this slice. It exposes its exact run identity, owned workflow snapshot, current phase, and terminal marker. Durable transition events will be a separate decision and implementation slice.

Starting or loading does not select an edge, acknowledge or evaluate a gate, invoke an action, skill, tool, provider, agent, or human, grant permission, schedule work, or modify registry topology.

** Alternatives considered
:PROPERTIES:
:CUSTOM_ID: alternatives-considered
:END:
*** Persist only workflow and phase IDs
:PROPERTIES:
:CUSTOM_ID: persist-only-workflow-and-phase-ids
:END:
That would make replay depend on whichever definition happens to be registered later. Definition replacement, package removal, or even authored-order changes could silently change transition meaning. An owned snapshot keeps provenance deterministic.

*** Persist a content hash and reload the package
:PROPERTIES:
:CUSTOM_ID: persist-a-content-hash-and-reload-the-package
:END:
A hash can prove identity only after another artifact store and reacquisition contract exist. It does not itself make the definition available for local replay. The small validated topology is the minimum self-contained state.

*** Add durable transition events immediately
:PROPERTIES:
:CUSTOM_ID: add-durable-transition-events-immediately
:END:
Advancement requires concurrency behavior, expected versions, event payload semantics, gate acknowledgement provenance, and atomic state projection. Starting and replaying immutable provenance is independently useful and keeps that policy separately reviewable.

*** Persist cursor memory directly
:PROPERTIES:
:CUSTOM_ID: persist-cursor-memory-directly
:END:
The cursor borrows process-local topology and is intentionally not a persistence schema. A typed versioned event keeps storage independent from Rust memory layout and lifetimes.

** Consequences
:PROPERTIES:
:CUSTOM_ID: consequences
:END:
*** Positive
:PROPERTIES:
:CUSTOM_ID: positive
:END:
- Every run permanently identifies the exact topology it selected.
- Replay is independent of mutable registries and extension files.
- Duplicate starts and malformed histories fail closed through existing event-log contracts.
- No availability or persistence operation gains capability authority.
- Later transition events can refer to stable authored indexes in an owned snapshot.

*** Negative
:PROPERTIES:
:CUSTOM_ID: negative
:END:
- Topology is duplicated once per run.
- The first durable run cannot advance and has no terminal lifecycle beyond the starting phase.
- Public kernel constructors can still create malformed topology; this slice validates exact start resolution while later advancement must retain its existing fail-closed target checks.
- Schema migration, compaction, discovery, and deletion are deferred.

** Verification
:PROPERTIES:
:CUSTOM_ID: verification
:END:
The first slice follows RED→GREEN tests proving non-blank exact run identity, exact owned topology persistence, declared-start state, registry-free reopen and replay, atomic duplicate and invalid-start rejection, typed unsupported/malformed event rejection, and invalid-history rejection. The complete repository quality gate must remain green.

** Revisit when
:PROPERTIES:
:CUSTOM_ID: revisit-when
:END:
Reconsider this decision before durable advancement, definition deduplication or content addressing, run discovery, lifecycle termination or cancellation, action binding, gate evidence, scheduling, checkpoints or compaction, retries, compensation, concurrency, migration, deletion, or remote execution.
