* Development record schema version 1
:PROPERTIES:
:CUSTOM_ID: development-record-schema-version-1
:END:
A Vela development record captures one implementation episode as deterministic, reviewable JSON. The Rust types in =vela_dev::record= are the schema authority. Unknown fields, unsupported schema versions, and values outside the bounded enums are rejected during deserialization; cross-field rules are reported separately by semantic validation.

** Shape
:PROPERTIES:
:CUSTOM_ID: shape
:END:
#+begin_src json
{
  "schema_version": 1,
  "task": {
    "title": "Validate records",
    "objective": "Reject invalid evidence",
    "acceptance_criteria": ["valid records pass"]
  },
  "attempts": [{
    "summary": "Implemented validation",
    "outcome": "success",
    "diagnostic": null,
    "patch": "crates/vela-dev/src/record.rs"
  }],
  "outcome": {
    "summary": "Validation works",
    "verified": true,
    "verification": [{"command": "just verify", "status": "passed"}]
  },
  "lessons": ["Keep validation deterministic"],
  "provenance": {
    "repository_path": "crates/vela-dev/src/record.rs",
    "url": "https://github.com/Knosence9/project-vela"
  },
  "sanitation": {"passed": true, "blockers": []},
  "trust": "curated",
  "example": {"type": "positive", "rejection_rationale": null}
}
#+end_src

Bounded values are:

- =attempts[].outcome=: =success=, =failure=, or =blocked=
- =outcome.verification[].status=: =passed=, =failed=, or =not_run=
- =trust=: =untrusted=, =reviewed=, or =curated=
- =example.type=: =positive= or =negative=

Version 1 requires non-empty task title, objective, and acceptance criteria. A verified outcome needs a passing verification. Curated evidence cannot end with a failed verification. Negative examples need an attempt diagnostic or rejection rationale. Repository paths are relative and cannot traverse parent directories, provenance URLs use HTTPS, and obvious secrets and absolute home-directory paths are rejected. Sanitation cannot pass with unresolved blockers.

** Validation CLI
:PROPERTIES:
:CUSTOM_ID: validation-cli
:END:
#+begin_src sh
nix develop --command cargo run --locked -p vela-dev -- record validate path/to/record.json
#+end_src

Exit status is =0= for valid records, =1= for records with semantic issues, and =2= for unreadable or malformed records. Semantic diagnostics are written to stderr as =<field path>: <stable code>: <message>= and all detected issues are emitted in deterministic traversal order.

** Corpus storage and inspection
:PROPERTIES:
:CUSTOM_ID: corpus-storage-and-inspection
:END:
Curated, project-native records are stored as JSON below =corpus/development/=. The corpus inspector recursively discovers =.json= files and processes them in sorted relative-path order:

#+begin_src sh
nix develop --command cargo run --locked -p vela-dev -- corpus inspect corpus/development
#+end_src

Valid entries are listed on stdout before a final count. Human-readable relative paths use one quoted, debug-escaped field, so untrusted filename controls cannot create extra output lines or terminal effects and distinct non-UTF-8 filename bytes remain distinguishable on Unix. Record-level read, deserialization, and semantic failures are prefixed with that same escaped path field on stderr; inspection continues so the summary covers the whole corpus. Exit status is =0= when every discovered record is valid, =1= when any record is invalid, and =2= when the corpus root cannot be traversed.

** Deterministic corpus sampling
:PROPERTIES:
:CUSTOM_ID: deterministic-corpus-sampling
:END:
Select a bounded path-ordered sample only after validating every discovered record:

#+begin_src sh
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --trust curated
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --example negative
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --attempt-outcome failure
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --verification-status passed
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --verified true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --sanitation-passed true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-sanitation-blockers false
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-lessons true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-attempt-diagnostic true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-rejection-rationale true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-attempts true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-verification true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --repository-path crates/vela-dev/src/lib.rs
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --provenance-url https://github.com/Knosence9/project-vela
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --task-title "Validate records"
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --task-objective "Check every record"
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --acceptance-criterion "valid records pass"
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --attempt-summary "Implemented validation"
#+end_src

The required limit is from =1= through =1024=. The optional =--trust= filter accepts exactly =untrusted=, =reviewed=, or =curated=; =--example= accepts exactly =positive= or =negative=; =--attempt-outcome= accepts exactly =success=, =failure=, or =blocked=; =--verification-status= accepts exactly =passed=, =failed=, or =not-run= (the CLI spelling for schema value =not_run=); and =--verified=, =--sanitation-passed=, =--has-sanitation-blockers=, =--has-lessons=, =--has-attempt-diagnostic=, =--has-rejection-rationale=, =--has-attempts=, and =--has-verification= each accept exactly =true= or =false=. Attempt-outcome and verification-status filters match a record when at least one =attempts[]= entry or =outcome.verification[]= check respectively has the exact requested value; records without the corresponding entries do not match. The verified and sanitation-passed filters match the exact aggregate =outcome.verified= and =sanitation.passed= booleans. The blocker, lesson, attempt-presence, and verification-presence filters match =true= when =sanitation.blockers=, =lessons=, =attempts=, and =outcome.verification= respectively are non-empty and =false= when the selected list is empty. The diagnostic filter matches =true= when any =attempts[].diagnostic= field is non-null and =false= when every diagnostic is null, including records with no attempts. The rationale filter matches =true= when =example.rejection_rationale= is non-null and =false= when it is null; an omitted optional field deserializes to the same absent value as JSON =null=. The optional =--repository-path= filter compares the caller's UTF-8 value to =provenance.repository_path= with exact, case-sensitive equality. It does not trim, normalize separators, resolve paths, inspect the filesystem, or infer related files. The optional =--provenance-url= filter compares the caller's UTF-8 value to =provenance.url= with exact, case-sensitive equality. It does not trim, normalize, parse, fetch, or otherwise dereference the URL. The optional =--task-title= filter compares the caller's UTF-8 value to =task.title= with exact, case-sensitive equality. It does not trim, normalize, tokenize, score, or interpret title text. The optional =--task-objective= filter compares the caller's UTF-8 value to =task.objective= with the same exact, case-sensitive equality and does not trim, normalize, tokenize, score, or interpret objective text. All filters compose conjunctively and apply before the limit. With no filters, every valid record is eligible; an empty match emits =[]= and succeeds. Output is one compact JSON array containing each selected relative =path= and complete =record=.

The optional =--acceptance-criterion= filter matches when any =task.acceptance_criteria[]= entry equals the caller's UTF-8 value exactly and case-sensitively. It does not trim, normalize, perform fuzzy matching, or infer related criteria. Like every other predicate, it is applied before the limit and composes conjunctively with selected filters.

The optional =--attempt-summary= filter matches when any =attempts[].summary=
entry equals the caller's UTF-8 value exactly and case-sensitively. It does not
trim, normalize, perform fuzzy matching, or infer from diagnostics, patches,
outcomes, or other fields. Records without attempts do not match. Like every
other predicate, it is applied before the limit and composes conjunctively with
selected filters.

Sampling emits no partial stdout. An unreadable corpus root exits with status =2=. An unreadable record, malformed JSON, semantic validation failure, or non-UTF-8 relative record path exits with status =1= after deterministic diagnostics prefixed by the same quoted, debug-escaped path field used by inspection. Discovery neither follows symbolic links nor treats non-regular =.json= entries as records; Unix reads reject candidates replaced by a final symbolic link or non-regular entry while accepting replacements that remain regular files. Sampling is read-only and performs no scoring, indexing, fuzzy retrieval, semantic inference, network access, mutation, or additional filesystem access based on the repository-path, provenance-URL, task-title, task-objective, acceptance-criterion, or attempt-summary predicates.
