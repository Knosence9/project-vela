** North star
:PROPERTIES:
:CUSTOM_ID: north-star
:END:
Vela is not intended to be a passive chatbot. She should notice conflict, challenge weak assumptions, remember useful lessons, improve her procedures, and build missing tools within explicit safety and review boundaries.

The system is guided by one engineering rule:

#+begin_quote
Models reason, decide, synthesize, and communicate. Code parses, validates, schedules, checks, records, and enforces contracts.
#+end_quote

** Bootstrap loop
:PROPERTIES:
:CUSTOM_ID: bootstrap-loop
:END:
Project Vela develops through an evidence-producing loop:

#+begin_src text
External Rust references
        ↓
Retrieve relevant patterns
        ↓
Implement a focused Vela change
        ↓
Format · compile · lint · test · review
        ↓
Correct and verify
        ↓
Capture the development episode
        ↓
Grow the Vela-native corpus
        ↺
#+end_src

External Rust datasets help the assistant write better Rust. At the same time, Vela's own implementation produces higher-value project-native examples: tasks, context, patches, diagnostics, corrections, rationale, tests, and verified outcomes. Vela will eventually inherit this evidence from her own development.

** Intended architecture
:PROPERTIES:
:CUSTOM_ID: intended-architecture
:END:
Vela's small, inspectable Rust kernel will eventually own:

- identity and behavioral policy
- task and session lifecycles
- durable memory and event replay
- tools, skills, workflows, and extensions
- permissions and isolation
- observability and deterministic validation
- controlled, auditable self-improvement

Existing Rust frameworks may be studied or integrated, but Vela should not be a thin wrapper around one framework.

** Development environment
:PROPERTIES:
:CUSTOM_ID: development-environment
:END:
Nix is the supported development entry point. The flake pins the Rust toolchain, Rust quality tools, GitHub tooling, formatters, native libraries, and CI utilities used by the project:

#+begin_src sh
nix develop
#+end_src

Run a single command without entering an interactive shell with:

#+begin_src sh
nix develop --command <command>
#+end_src

The committed =flake.lock= keeps local development and CI reproducible across x86-64 Linux, ARM64 Linux, and Apple Silicon macOS.

Run the complete local quality gate with:

#+begin_src sh
nix develop --command just verify
#+end_src

Before arming squash auto-merge for a pull request, verify its exact head and
review evidence with:

#+begin_src sh
head=$(nix develop --command git rev-parse HEAD)
nix develop --command scripts/verify-merge-readiness <pr-number> "$head"
#+end_src

The read-only verifier reports deterministic =READY= or =BLOCKED= diagnostics;
it never merges the pull request. See [[file:CONTRIBUTING.org][=CONTRIBUTING.org=]] for
the fail-closed review contract.

Project Vela is Org-native. Emacs Org Mode is the primary authoring workbench for plans, architecture decisions, implementation documentation, and repository guidance; GitHub renders those same =.org= sources for remote review. The repository does not maintain parallel Markdown copies. See [[file:CONTRIBUTING.org][the Org source policy]] for the enforced contract and optional Obsidian interoperability.

** Secret management

secret values must remain in an external SecretSpec provider such as the system
keyring. Set up your preferred provider once, verify the required values, and
then run commands with only their declared secrets injected:

#+begin_src sh
nix develop --command secretspec config init
nix develop --command secretspec check
nix develop --command just with-secrets cargo run --locked -p vela-dev -- --help
#+end_src

CI and the local quality gate use an ephemeral, permission-restricted dotenv
fixture containing a disposable test value. They remove it on exit and never
require or print a developer credential. See
[[file:docs/adr/0001-declarative-secret-management.org][=docs/adr/0001-declarative-secret-management.org=]]
for the trust boundary and rationale.

Verified project-native records live under =corpus/development/=. Inspect every JSON record recursively, in deterministic relative-path order, with:

#+begin_src sh
nix develop --command cargo run --locked -p vela-dev -- corpus inspect corpus/development
#+end_src

Inspection prints each valid record with a quoted, debug-escaped relative path and an aggregate summary. The escaped form preserves distinct non-UTF-8 filename bytes on Unix. Inspection continues past malformed, unreadable, or semantically invalid records, emits diagnostics prefixed by the same control-safe path field, and exits non-zero when any record is invalid.

Select at most 32 fully validated records in deterministic relative-path order, optionally restricted to one schema-v1 trust level, example type, attempt outcome, and verification status, with:

#+begin_src sh
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --trust curated
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --example negative
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --attempt-outcome failure
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --verification-status passed
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --verified true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --sanitation-passed true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-sanitation-blockers false
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-lessons true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-attempt-diagnostic true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-rejection-rationale true
nix develop --command cargo run --locked -p vela-dev -- corpus sample corpus/development 32 --has-attempts true
#+end_src

Sampling validates the entire discovered corpus before emitting one compact JSON array of relative paths and complete records. Limits must be from 1 through 1024. The =--example= filter accepts exactly =positive= or =negative=; =--attempt-outcome= accepts exactly =success=, =failure=, or =blocked= and matches a record when any attempt has that outcome; =--verification-status= accepts exactly =passed=, =failed=, or =not-run= and matches when any =outcome.verification[]= check has that status; and =--verified=, =--sanitation-passed=, =--has-sanitation-blockers=, =--has-lessons=, =--has-attempt-diagnostic=, =--has-rejection-rationale=, and =--has-attempts= each accept exactly =true= or =false=. The first two boolean filters match the aggregate =outcome.verified= and =sanitation.passed= decisions; the blocker, lesson, and attempt-presence filters match whether =sanitation.blockers=, =lessons=, and =attempts= respectively are non-empty; the diagnostic filter matches whether any =attempts[].diagnostic= field is non-null; and the rationale filter matches whether =example.rejection_rationale= is non-null. These predicates are independent: aggregate decisions are not inferred from individual checks or blocker presence, blocker presence is not inferred from =sanitation.passed=, lesson and attempt presence do not inspect or infer entry contents, diagnostic presence does not inspect, trim, normalize, or infer diagnostic text or attempt outcomes, and rationale presence does not inspect, trim, normalize, or infer rationale text or example type. Records without the corresponding entries do not match existential attempt or verification filters; a record without attempts has neither attempt presence nor an attempt diagnostic. All filters compose conjunctively without changing path order or limit behavior. Empty matches succeed with =[]=; traversal, record, JSON, and semantic failures produce no partial stdout, and record diagnostics use quoted, debug-escaped relative paths. Sampling is read-only and uses no randomness, ambient state, network access, scoring, or indexing.
